Signaling UX — Practical-first storyboard

A second ordering for the same wizard, drawn in the same design language as the original proposal so the two can be compared directly. It asks what the railroad must do before it asks what signaling system governs the location, and it offers familiar signaling as a complete answer rather than a preview of a better one. Everything downstream of the wizard — bring-up, the facility card, capacity, APB and CTC — is unchanged from the original and is deliberately not repeated here. Two signals are built below: the common case first, then the hard one.

What this document is testing

Not whether the model can express real signaling — the original answers that, and this document changes nothing about the model. What is on trial here is the order of the questions. The original opens by asking the user to name a signaling system (ABS, APB, interlocking) and the signal's role within it. This version opens by asking how the track beyond the signal is used, and maps the answer to a signaling system privately.

  1. Signaling system, and this signal's role in it
  2. Signaling discipline, giving the indication set
  3. Signal style
  4. What it protects
  5. Wire the lamps

Practical-first ordering

  1. How the track beyond this signal is used
  2. How closely to follow a prototype
  3. Signal style
  4. What it protects, per route
  5. Confirm the derived behaviour

Lamp wiring is unchanged and folded into step 4.

Two questions we would like answered with a counter-example, not an opinion:
1. Name a location where answering “how is this track used” first leads the user to the wrong signal — somewhere the signaling system genuinely has to be stated up front.
2. Name an indication set that the Practical answer produces badly enough that the user would have been better served being asked for a rulebook on screen one.

If you know prototype signaling

  1. Can a modeler answer the four Track use choices in §1 without signaling expertise?
  2. Does Practical read as a complete choice, or as a lesser one?
  3. The hard case in §3 introduces the words Medium Clear and Medium Approach at the confirm step, having avoided all jargon until then. Is that the right moment, too late, or an argument against hiding it at all?
  4. Is “what happens beyond this signal” the right framing, or should it be “what happens at this signal”?

If you know Signal-LCC / LCC hardware

  1. The user never names the hardware. Bowties allocates drivers, aspects and — for APB and CTC — a second board. Is silent allocation acceptable, or does the board have to be visible earlier?
  2. In §2, filtering the prototype catalog by what the hardware can display: useful, or does it hide entries people will go looking for?
  3. §3 spends 6 of 16 lamp drivers on one signal without the user asking for a second head. Is the capacity readout at the confirm step early enough?
  4. Are placeholders for not-yet-created masts a good idea independent of this ordering?
The signaling data here is illustrative, not authoritative. Indication names, lamp arrangements and speed pairings are drawn from common speed-signaling practice to make the screens concrete. Please correct them — but please treat mistakes in the data separately from problems with the ordering. They are different critiques.

2. Fidelity — what Prototype and Custom look like when chosen

Step 2 is the load-bearing claim of this ordering: that Practical can be a complete answer without making prototype fidelity feel like a locked door. Both other branches are shown here so reviewers can judge whether the door is obvious enough.

Prototype rulebook

The user picks a railroad or signaling family. Bowties takes the indication table, the speeds, the normal/diverging applicability and the cascade policy from the catalog entry. The catalog entries are ordinary signal types with no special status — the same objects the Custom branch produces.

PRR 1956 position light
Vertical row = Clear · 3 of 4 lit lamps · 7 drivers
Nothing about this is red-over-green. The three degrees of freedom — a name, up to four lit lamps, a published speed — cover a position light and a color light without a special case, which is what makes the Practical default safe rather than limiting.

Custom

The original's signal type editor, reached from step 2 rather than being the default path. Heads, lamps per head, indications, published speeds, flashing and cascade are all editable, and the indication list is filtered by what the mast can physically show.

Those two speed columns are still the entire logic. Practical fills them in from the track use; Prototype takes them from the catalog; Custom lets the user set them. All three land in the same place.
The risk this ordering takes. A user who wants prototype fidelity must first answer a question about track use that feels beneath them, then find fidelity on screen two. The original puts their question first and the beginner's question second. Which user should have to scroll past the other one's question? — that is the whole disagreement between these two documents, stated as plainly as we can.

4. What actually got harder

Both signals used the same five steps and the same four questions. Everything below is what the wizard added on its own, without a further question being asked.

The good news for this ordering. The step count did not grow, the vocabulary did not grow until the last screen, and the hard case never required the user to know that “interlocking” was the word for what they were building. Four plain questions carried a two-head speed-signaled interlocking mast.
The bad news for this ordering. Three separate decisions — a second head, doubled driver cost, and two new indication names — were made for the user and revealed late. In the original the user commits to “interlocking home signal” on screen one, so the same three consequences read as things they asked for. Deferred surprise is the price of a gentler opening question.

6. Where this ordering is weakest

Stated plainly, so a reviewer comparing the two documents can weigh the trade rather than being sold one side of it.

Costs of asking track use first

  • Four words carry too much. “A junction” spans a siding turnout and a yard throat; the original's “interlocking home signal” does not.
  • Consequences arrive late. Head count at step 3, driver cost and new vocabulary at step 5.
  • The expert is served second. Someone who knows they want NORAC must answer a beginner's question before reaching fidelity.
  • The jargon is deferred, not removed. Operators still have to learn Medium Clear.

Benefits of asking track use first

  • The common case takes four obvious answers and never names a signaling system.
  • No impossible combinations. Style is chosen after Bowties knows the indication count, so an unbuildable pairing is never offered.
  • Hardware consequence appears at step 1 — including “this needs a Tower LCC+Q”, before any effort is invested.
  • Practical is a complete answer, with prototype fidelity one click away rather than a prerequisite.
What we are actually asking you to choose between. Both documents build the same two signals, from the same model, ending in the same derived table. The original front-loads a question only an informed user can answer, and everything after it reads as consequence. This one front-loads a question anyone can answer, and pays for it with three decisions made silently on the user's behalf. Which failure would you rather debug at 2 a.m. before an operating session?
