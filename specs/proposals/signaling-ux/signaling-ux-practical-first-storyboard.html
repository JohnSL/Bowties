Signaling UX — Practical-first storyboard

The shipping direction for the same wizard, drawn in the same design language as the original proposal so the two can be compared directly. It asks what this signal protects before anything else, with recognisable railroad objects as the choices — a stretch of track, a junction or crossing, or a special controlled location. A dedicated plant step then captures what the thing being protected actually looks like (shape, routes, how it terminates), using schematic tiles as its picker so a modeler can recognise their layout at a glance instead of translating prose into pictures. Only then does Bowties produce the indication table from two controls — signaling family (speed vs. route) and a three-rung vocabulary ladder (Essential, Common, or a Rulebook chosen from a JMRI-derived catalog). The number of heads and the head style are consequences of that indication table, not peer questions. Two signals are built below: the common case first, then the hard one.

Design decisions and their rationale live in design-decisions.md; the durable non-negotiables live in the charter.

Scope — four phases

Bowties signaling delivers in four named phases. Phases are scope commitments, not release commitments — a phase may span multiple releases; a phase is done when it covers its audience, not when a specific release ships. See the charter for the full phasing rules and design-decisions.md for the rationale.

  1. Phase 1 — Signal Masts. Every single-signal facility (block, distant, yard limit, single-signal at a turnout / holdout / bridge / boundary / spur end). One facility type, 5-step wizard, no Plant object. Signal LCC's per-mast cascade handles block state, next-mast reference, turnout binding, and local overrides. Multi-signal facilities work as N independent Masts — functionally complete, ergonomically tedious.
  2. Phase 2 — Signal Plants. Introduces the Signal Plant object as an ergonomic layer for multi-signal facilities. Flagship tile: passing siding. Also multi-signal single-turnout interlocking, APB coordination, signal-type reuse. Includes a Mast → Plant conversion path so users promote phase-1 siblings into a Plant without redoing configuration.
  3. Phase 3 — Additional common Plant tiles + specialty depth. Wye, single crossover, double crossover, interlocked diamond, funnel, multi-signal bridge / holdout / boundary, signal-type authoring, distant chaining edge cases.
  4. Phase 4 — Custom / compound plants. Facilities whose topology varies per site (e.g. Mitchell Schuessler's 112R). Signal Plant with imported topology from JMRI Layout Editor. Bowties compiles to STL for Signal-LCC as a generation target.

What this storyboard shows. §1 is the phase-1 Signal Mast walkthrough (block signal, the exemplar case). §1b is a preview of the phase-2 Signal Plant walkthrough using a passing siding — sketched at lower fidelity while the multi-signal-per-plant UX is still being iterated. §2–§6 discuss vocabulary depth, a two-head junction case (still a Mast under phase 1), and pedagogical framing that applies across phases. Phase 3 and phase 4 are described but not mocked.

What this document is testing

Not whether the model can express real signaling — the original answers that. What is on trial here is the order of the questions and where each decision lives. The original opens by asking the user to name a signaling system (ABS, APB, interlocking) and the signal's role within it. This version opens by asking what this signal protects, gives the plant its own step so shape / routes / termination are visible first-class questions (not adaptive text hidden on the aspect screen), and only then produces the indication table from two controls: signaling family and a three-rung vocabulary ladder whose top rung — Rulebook — opens a searchable JMRI-derived catalog with full and reduced-appearance variants.

Practical-first ordering

  1. What this signal protects (block / turnout / single track / dispatcher point)
  2. Aspect vocabulary — signaling family (speed · route) plus a three-rung vocabulary ladder (Essential · Common · Rulebook, where Rulebook opens a searchable JMRI-derived catalog). Produces the indication table.
  3. How to display those N aspects on H heads — head style, filtered by what can display them
  4. Bindings — block name, turnout, next signal, lamp wiring
  5. Confirm the derived behaviour

5 steps in phase 1 because every phase-1 facility is a Signal Mast — every single-signal case, whether it protects a block, a turnout, a holdout, a bridge, or a boundary. Signal LCC's per-mast cascade handles the details. A dedicated Plant step appears in phase 2 for multi-signal facilities (passing siding, multi-signal interlocking, etc.) as an ergonomic layer over the same substrate — see the phase-2 preview in §1b. Layout defaults for family and vocabulary-ladder rung come from built-in fallbacks (speed · Essential) until the modeler opens the on-demand Layout defaults dialog from step 2 or the settings menu. After the first signal, a small confirm offers to save the modeler's choices as new defaults. Any signal can override in one click.

Three questions we would like answered with a counter-example, not an opinion:
1. Name a location where answering “what does this signal protect” first leads the user to the wrong signal — somewhere the signaling system genuinely has to be stated up front.
2. Name an indication set that the Essential vocabulary rung produces badly enough that the user would have been better served being offered Common as the default.
3. Is speed vs. route as a visible layout default (with per-signal override) the right resolution, or does it need to be per-territory now?

If you know prototype signaling

  1. Can a modeler answer the four What does this signal protect choices in §1 without signaling expertise?
  2. Do the vocabulary-ladder rungs (Essential / Common / Full, plain-name or rulebook) read as neutral operator-ergonomic choices, or as a lesser-vs-real hierarchy?
  3. Speed / route is surfaced as a segmented control on the aspect step with a visible layout default in the wizard chrome. Is that the right level of visibility, or should it be its own screen?
  4. The hard case in §3 still lands Medium Clear and Medium Approach on the confirm screen when Common is chosen. Is the pocket-card render on that screen enough to make the trade-off legible?

If you know Signal-LCC / LCC hardware

  1. The user never names the hardware. Bowties allocates drivers, aspects and — for APB and CTC — a second board. Is silent allocation acceptable, or does the board have to be visible earlier?
  2. The display step filters the head-style catalog by “how many aspects on how many heads.” Useful, or does it hide entries people will go looking for?
  3. §3 spends 6 of 16 lamp drivers on one signal without the user asking for a second head. Is the capacity readout on the aspect step (derived from the aspect table) early enough?
  4. Are placeholders for not-yet-created masts a good idea independent of this ordering?
The signaling data here is illustrative, not authoritative. Indication names, lamp arrangements and speed pairings are drawn from common speed-signaling practice to make the screens concrete. Please correct them — but please treat mistakes in the data separately from problems with the ordering. They are different critiques.

1. Phase 1 — Signal Mast walkthrough (block signal, start to finish)

Phase 1 covers every single-signal facility as a Signal Mast. Block signals, distants, yard limits, single-signal at a turnout / holdout / bridge / boundary / spur end — all one facility type, all one 5-step wizard, no Plant object. This walkthrough uses plain double track with no turnout and no dispatcher because that is the signal most modelers place most often; the same wizard handles the other Mast cases with a different Frame 1 tab choice and appropriate cascade / binding follow-ups. Signal position is picked on the diagram, not in a second grid. Each shape's preview diagram shows radio markers only at valid entry points — three for a single turnout (points end / main leg / diverging leg), four for a three-way, more for a crossover, three for a wye, and just one fixed marker for a diamond. 2. Vocabulary ladder — three rungs, backed by a JMRI-derived rulebook catalog

Step 3 is the load-bearing part of this ordering. An earlier draft exposed three controls (signaling family, aspect set size, fidelity) and later collapsed size and fidelity into a six-rung ladder. The current version goes one step further: three rungs — Essential, Common, Rulebook — with the JMRI-derived rulebook catalog carrying the reduced-appearance variants that earlier rungs hand-authored. Family stays separate because it is genuinely orthogonal to naming.

The two axes, honestly named

  • Family — speed vs. route. Changes the shape of the indication table (whether diverging-speed distinctions exist), not the naming.
  • Vocabulary ladder — Essential (plain), Common (plain), or Rulebook. One ordered choice about how deep to go with naming.
Prototype names live in the catalog. The earlier draft split naming into four hand-authored rungs (Essential/Common × plain/rulebook names). The JMRI catalog already ships reduced-appearance variants of most rulebooks; picking one gives you prototype names at operator-friendly length without a parallel ladder to maintain.

The three rungs

  1. Essential — 3–4 plain-English aspects, Bowties-picked. Business-card sized. The 80% default.
  2. Common — 5–7 plain-English aspects. Adds diverging-speed / extended-approach indications. Index-card sized.
  3. Rulebook — pick from the JMRI-derived catalog. Full and reduced-appearance variants coexist; a small badge distinguishes reduced entries.
Rulebook picker appears only on the Rulebook rung. Essential and Common have no rulebook selector. Rulebook shows a search box, a full/reduced filter, and the catalog list. Era is a sub-selector inside the rulebook picker that only appears for rulebooks with meaningful era-dependent variants.

Rulebook rung — how a modeler picks a rulebook

The user searches or scrolls the catalog. Bowties takes the indication table, the speeds, the normal/diverging applicability and the cascade policy from the selected catalog entry. Reduced-appearance variants are ordinary catalog entries with a reduced badge, not a separate ladder rung. The rulebook may imply a head style (PRR → position light); the display step preselects it.

6. Where this ordering is weakest

Stated plainly, so a reviewer comparing the two documents can weigh the trade rather than being sold one side of it.

Costs of asking what it protects first

  • Three broad choices still carry a lot. “A junction or crossing” spans a siding turnout and a yard throat; the original's “interlocking home signal” does not.
  • Step 3 has two controls; the Rulebook rung unfolds a picker. Family plus a three-rung vocabulary ladder (Essential / Common / Rulebook); the Rulebook rung shows a searchable catalog with a full/reduced filter. The original's single Practical / Prototype / Custom pick reads simpler at a glance.
  • The expert is served second. Someone who knows they want NORAC must answer a beginner's question before reaching the Rulebook rung.
  • The jargon is deferred, not removed. Operators still have to learn Medium Clear the moment the vocabulary ladder is stepped up to Common.

Benefits of asking what it protects first

  • The common case still takes four obvious answers per signal, plus one one-time layout-level question.
  • Aspects, heads and drivers are shown together on step 3. Nothing about head count or driver cost is a surprise at step 4.
  • Speed vs. route is visible. Layout default in the wizard chrome; one-click override per signal. A 20% modeler helping an 80% modeler edits one control, not a hidden rulebook.
  • Operator ergonomics are a first-class dial. Essential / Common / Full prototype is a legitimate choice; the confirm screen offers a pocket-card render sized to match.
  • Hardware consequence appears at step 1 — including “this needs a Tower LCC+Q”, before any effort is invested.
  • No impossible combinations. Style is filtered by the aspect table, so an unbuildable pairing is never offered.
What we are actually asking you to choose between. Both documents build the same two signals, from the same model, ending in the same derived table. The original front-loads a question only an informed user can answer, and everything after it reads as consequence. This one front-loads a question anyone can answer, and pays for it with three decisions made silently on the user's behalf. Which failure would you rather debug at 2 a.m. before an operating session?
