Panel facility

Block indicator lamps nearly always live on a panel or fascia. This proposal replaces "one Block Indicator facility per LED" with one facility per panel. You choose the blocks the panel shows, then wire each block to its lamp, the same way the signals editor wires each signal.

Proposal
Mockup for Spec 021 (spec.md). Revised 2026-11-25. Where this mockup and the spec differ, the spec wins. Sections 1–4 follow what the modeler sees, in order: Add facility, the Blocks step, the Wiring step, then the Railroad tab. The three screens share one set of mockup data, so changes in one step show up in the next. Background, options and open questions come after.

2. Blocks step

This is what the modeler sees first: an empty panel. Add blocks one at a time, or all of a signals facility's or a detector board's blocks at once. The order here is the panel's order, used on the Wiring step and the Railroad tab.

    Design notes

    • Try it: add Mainline Eastbound, then a helix block, then reorder or remove one.
    • "Add all blocks from" is only a way to select. The panel doesn't follow the signals facility afterwards, and removing that facility doesn't change the panel.
    • Blocks are listed by detector board. The meta line names any signals facility a block belongs to, as context.
    • No track diagram. A panel's blocks have no travel order or connections of their own, so a diagram would need a track model for the whole layout or a freehand editor. See decision D4.
    • Next is available with no blocks, but the Wiring step has nothing to show until there is one.

    3. Wiring step

    Pick a block, then pick its lamp's board and pin. The pins appear as the board labels them, so a custom PCB's own layout decides which pin each block uses. Done is on this step.

      Design notes

      • The mockup data wires the four Main blocks to pins out of order (#9, #3, #14, #6), as a PCB layout might.
      • Clicking the block's own pin again clears it, as in the signals Wiring step. There is no separate Clear button.
      • Pins this panel already uses show their block's name. Choosing one moves that pin to the selected block, and the block that had it then needs a lamp. The status line says so.
      • Pins a mast or another facility uses can't be chosen. Pins used outside Bowties show their Lamp Description and can be released, as in the signals Wiring step.
      • "Lit when" is one panel setting. Each block can override it, for example for a "clear" lamp on a green LED.
      • Done saves even if some blocks have no lamp yet. The panel is then Incomplete and the card says how many need a lamp.
      • Each wired block creates one lamp-indicator channel on a Direct Lamp Control row, with both Lamp On and Lamp Off set. The Lamp Description defaults to the block name.

      • The lamp state comes from the lamp channel, not the block. If a write didn't take, the lamp and the block disagree, and the tile shows it.
      • Blocks that also belong to Mainline Eastbound appear on both cards. The panel uses those occupancy channels. It doesn't own them (Q1).

      5. Why a panel

      Today a modeler with 24 block lamps creates 24 Block Indicator facilities. Each one pairs one occupancy channel with one lamp, which is a named bowtie and little else.

      ConfigurationBowtiesRailroad

      Facilities · today

      A. Keep one per indicator today

      • No work. It already ships.
      • The list grows with the number of LEDs.
      • Nothing records that the lamps share a panel.

      B. Lamps inside Automatic Block Signals

      • Reuses the block list and Wiring step.
      • Many fascias have lamps and no signals.
      • A panel spans lines, sidings, yards and parts of plants. A signals facility is one direction of one line.
      • Rebuilding the signals would disturb the panel.

      C. A bulk "Block Indicators" facility

      • Fixes the card count.
      • Named for the mechanism, not the place.
      • Turnout lamps and repeaters would need sibling facilities.

      D. Panel facility this mockup

      • One facility per physical panel, which matches how lamps are actually installed.
      • Its Wiring step reuses the signals editor's pattern.
      • Later row types extend it without new facilities.
      • Needs a rule for channels that several facilities use (Q1).

      6. Decisions so far

      Made while iterating on this mockup. Revisit any of them by editing this list.

      D1. Wire block by block, not by automatic pairing.

      Panel PCBs route pins to suit the board, so the pin for each block is a deliberate choice. An earlier draft paired blocks with pins in order. It was dropped.

      D2. Two steps, Blocks then Wiring, with Done on Wiring.

      Matches the signals editor. The earlier draft's "Add indicators" sub-dialog, which had its own commit button inside the editor, was dropped.

      D3. Choose the block first. No pin-first view for now.

      Choosing a pin and then its block would help someone working from a schematic. It is deferred until someone asks for it.

      D4. No panel diagram.

      The signals diagram comes from that facility's own data: blocks in travel order, joins and turnouts. A panel has only a set of blocks, so drawing one would need a track model for the whole layout or a freehand editor. Lists are used instead.

      D5. No "fill the rest in order" helper.

      It follows from D1. It can come back if hand-wired fascias show a need.

      7. Later row types

      This is why the facility is called Panel rather than Block Indicators. When these arrive, the Blocks step becomes "What this panel shows" and the Wiring step's pin grid takes the row's pins.

      Turnout position

      turnout-position (normal / reverse)
      → 2 lamps, or 1 bicolor

      Needs a turnout-position role. The Wiring detail shows two pin pickers.

      Signal repeater

      signal-indication (Stop / Approach / Clear)
      → R/Y/G lamps or 1 bicolor

      Uses the signal channels Automatic Block Signals already creates. Open: can direct lamps follow aspects cleanly, or does a repeater need a mast of its own?

      Push button / toggle

      panel input → turnout command, route request

      The panel produces events instead of consuming them. A first step toward CTC-style panels.

      8. Migration from Block Indicator

      9. Open questions

      Ordered by how much they shape the data model.

      Q1. Do facilities own channels or just use them?

      Today a channel is bound to at most one Facility Slot. A panel that shows blocks from a signals facility, or later repeats a signal, needs several facilities to use one channel.

      Leaning: a facility owns the channels it creates (lamps, signal indications) and uses any others. Removing a facility deletes only what it owns.

      Q2. Can a panel span boards?

      The mockup allows a board choice per block. A large panel might be wired to two boards.

      Leaning: yes. The Wiring detail remembers the last board chosen, so a one-board panel never touches the board picker.

      Q3. Does the fixed-slot Behavior Template survive?

      Block Indicator is its only user. Automatic Block Signals already keeps its own record. Panel would do the same.

      Q4. Can a block appear on two panels?

      For example a helix lamp on both the upper and lower fascia. With Q1's "uses" rule, yes: each panel owns its own lamp.

      Q5. Which boards besides Signal LCC can drive lamps?

      The lamp style today is single-led-direct-lamp on Signal LCC. Tower LCC and other boards would add styles for the same lamp-indicator role. The pin grid has to come from the style.

      Q6. Is "Panel" the right name?

      Alternatives: Control Panel, Fascia. Check the choice against the glossary's avoid-lists.
